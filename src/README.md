# Клиентские модули АвтоЖурнала

Данный каталог подготовлен по задаче **FE-003**. Пока приложение использует
статическую страницу `tempPage/index.html`, созданную в лабораторных № 4–5.
По FE-004 файл `src/main.js` подключён к `tempPage/index.html`: он переключает четыре страницы через hash-маршруты без перезагрузки.

| Каталог / файл | Назначение | Задача backlog |
| --- | --- | --- |
| `main.js` | Маршрутизация, обновление активной навигации и заголовка | FE-004 |
| `pages/` | Четыре раздела: главная, автомобиль, журнал, план ТО; статические макеты | FE-004 |
| `components/` | Общие кнопки, поля, карточки, пустое состояние, сообщения | FE-005 |
| `models/car.js` | Поля и проверка карточки автомобиля | FE-007 |
| `models/serviceEntry.js` | Поля и проверка события обслуживания | FE-009 |
| `models/maintenancePlan.js` | Поля и проверка плановой работы | FE-019 |
| `storage/localStorage.js` | Изолированный доступ к хранилищу браузера | FE-006 |

| `utils/maintenanceDue.js` | Проверка сроков ТО по дате и пробегу | FE-021 |

## Правила разработки

1. `pages/` используют `components/`, модели, `storage/` и `utils/`, но не
   реализуют самостоятельно чтение/запись `localStorage`.
2. `models/` и `utils/` не знают о DOM и не обращаются к браузерному хранилищу.
3. `storage/` хранит чтение и запись под ключами
   `autojournal_v1_car`, `autojournal_v1_entries`, `autojournal_v1_plans`.
   Реализовано в **FE-006**: безопасное чтение, запись и обработка ошибок.
4. Проект остаётся клиентским: нет backend, REST API, учётных записей и сетевых запросов.
5. Реализованы переходы между разделами (FE-004) и общие DOM-компоненты
   (`components/`, FE-005). Модели, хранение и расчёты пока остаются заготовками.
6. URL разделов: `#/home`, `#/car`, `#/journal`, `#/maintenance`. Ссылка
   открывает раздел без полной перезагрузки, работают Назад/Вперёд.

## FE-005: общие компоненты

- `Button.js`: единый элемент `<button>` для действий и `<a>` для переходов.
- `FormField.js`: поле + `label`, `required`, ошибка с `aria-describedby`, валидация.
- `SummaryCard.js`: карточка сводки, используется трижды на главной.
- `EmptyState.js`: состояние списка без записей, пример на странице журнала.
- `ErrorNotice.js`: общая ошибка формы (`role="alert"`).
- `DemoForm.js`: две тестовые формы в разделах «Автомобиль» и «Журнал».
  Форма только проверяет заполнение; изменение данных — **не FE-005**.

## FE-006: локальный слой данных

`storage/localStorage.js` предоставляет функции `readCar`, `readEntries`,
`readPlans`, `saveCar`, `saveEntries`, `savePlans` (и общие
`readLocalData`/`writeLocalData`). Они возвращают результат `{ ok, status, data? , message? }`,
а не выбрасывают исключения при ошибках доступа к браузерному хранилищу.

Ключи: `autojournal_v1_car`, `autojournal_v1_entries`, `autojournal_v1_plans`.
Пустое хранилище возвращает `null` для автомобиля и `[]` для списков.
Повреждённый JSON или сбой доступа возвращает безопасное состояние и сообщение,
не очищая сохранённые данные. Корневые типы данных проверяются; детальная
валидация полей относится к FE-007/009/019. В страницах пока демо-данные,
но при повреждённом хранилище отображается уведомление и безопасное состояние.
Формы начнут сохранять реальные данные в следующих задачах.

Тесты: `npm test`.

## FE-007: модель автомобиля

`models/car.js`: `validateCar(input)` нормализует четыре поля автомобиля
(`brand`, `model`, `year`, `currentMileage`) и возвращает ошибки по полям.
Проверка не обращается к браузеру и не сохраняет данные. При `ok: true`
результат `data` можно передавать в `storage.saveCar()` из FE-006.
Сборка интерфейса редактирования и вызов этих функций из формы — FE-008.


### FE-008 — форма карточки автомобиля

`pages/CarPage.js` реализует создание и изменение одного автомобиля на странице `#/car`.
Поля создаются переиспользуемым `components/FormField.js`; ошибки привязаны к полям.
`saveCarFormData()` проверяет значения функцией `models/car.js::validateCar` и
сохраняет корректные данные через `storage/localStorage.js::saveCar`.
Повреждённое хранилище не перезаписывается автоматически.
Тесты: `tests/fe008-car-form.test.mjs`.
Другие разделы приложения в FE-008 не меняются.


### FE-009 — модель журнала

`models/serviceEntry.js`: список допустимых категорий `SERVICE_ENTRY_TYPES`,
`validateServiceEntry()` с ошибками по полям и `createServiceEntry()` с новым
уникальным id. Поля: `id`, `type`, `date`, `mileage`, `description`, `amount`.
Дата должна существовать и иметь формат `YYYY-MM-DD`, описание обязательно,
пробег — неотрицательное целое, стоимость — число от нуля. Модуль не меняет
`localStorage` и не отображает интерфейс. Подключение формы и запись нового
события в `storage.saveEntries()` — FE-010.


**FE-010:** `pages/NewServiceEntryPage.js` создаёт форму записи события и через
`models/serviceEntry.js` добавляет валидную запись в массив из
`storage/localStorage.js`. Маршрут `#/journal/new` доступен с главной и журнала.
`pages/JournalPage.js` пока показывает минимальный список фактически сохранённых
записей; полная история по датам будет оформлена в FE-011.


## FE-011 — История обслуживания

- `utils/serviceHistory.js`: чистая сортировка событий по дате, без изменения массива.
- `pages/JournalPage.js`: читаемый список со всеми полями, пустое состояние и переход к созданию записи.
- История берётся только из `readEntries()` FE-006; функции поиска, фильтров и редактирования пока отсутствуют.

## FE-012: операции над существующими событиями

- `utils/serviceEntryActions.js` — обновление выбранной записи и подтверждённое
  удаление с безопасным чтением и записью в `localStorage` (FE-006).
- `pages/EditServiceEntryPage.js` — заполненная форма редактирования по ID;
  форма переиспользуется из `NewServiceEntryPage.js` (FE-010).
- `pages/JournalPage.js` — действия «Изменить» и «Удалить» для каждой записи;
  после подтверждённого удаления журнал перерисовывается без перезагрузки.
- FE-013 (поиск и фильтрация) пока не реализована.


### FE-014 — Краткая история на главной

`utils/recentServiceEntries.js` выбирает не больше трёх записей, используя сортировку FE-011 без изменения исходного массива. `pages/HomePage.js` читает `readEntries()` и создаёт краткие карточки. В шаблоне HTML больше нет фиктивных записей. Если журнал пуст, показывается `EmptyState` со ссылкой на новую запись. Ссылка «Все записи» ведёт к полной истории. Расходы и ближайшее ТО подключены в FE-017 и FE-023.

- **FE-015:** журнал использует одни и те же элементы метаданных на desktop и mobile; CSS перестраивает их на ширине до 620 px без создания дублирующей мобильной разметки.

## FE-016 — Расчёт расходов

`utils/expenses.js` экспортирует три чистые функции: `calculateTotalExpenses()`,
`calculateExpensesByCategory()` и `calculateExpenseSummary()`. На вход подаётся
массив `ServiceEntry` из модели FE-009 и необязательный период
`{ startDate, endDate }` в формате `YYYY-MM-DD`. Обе границы включаются;
пропущенные границы означают отсутствие ограничения. По четырём категориям
всегда возвращаются числовые суммы, включая нули. Суммы округляются после
суммирования до копеек, данные в хранилище не изменяются. Неверные записи
и некорректные границы приводят к понятным исключениям, а не к ложному итогу.
Вывод расходов на странице и выбор периода — отдельная задача FE-017.

Проверка: `node --test tests/fe016-expenses.test.mjs` и `npm test`.


### FE-019 — Модель планового ТО

`models/maintenancePlan.js` экспортирует поля модели, два допустимых статуса,
`validateMaintenancePlan()` с ошибками по полям и `createMaintenancePlan()`
с новым ID и исходным статусом `planned`. Контрольная дата и пробег
необязательны по отдельности, но без обеих точек план невалиден.
Хранение массива планов — готовый слой `storage/localStorage.js` (FE-006).
Интерфейс и вычисления сроков — будущие задачи FE-020/FE-021.

- **FE-020:** `pages/MaintenancePage.js` содержит форму создания плановой работы и базовый список сохранённых планов. `saveNewMaintenancePlan` использует модель FE-019 и хранилище FE-006; `createMaintenanceForm` переиспользует компоненты FE-005. Сроки, выполнение и просрочки будут реализованы в FE-021/022.

### FE-021 — определение наступления срока ТО

`utils/maintenanceDue.js` — чистый модуль без зависимости от интерфейса и
`localStorage`. Функция `getMaintenanceDueStatus(plan, { today, currentMileage })`
возвращает `state` (`planned`, `due`, `done`), `needsAttention`, а также
`dueByDate` и `dueByMileage`, чтобы будущая страница FE-022 могла объяснять
причину напоминания. Достаточно достичь **одного** из заданных порогов:
контрольной даты включительно или контрольного пробега включительно.
Для выполненного плана состояние всегда `done`, без повторного требования ТО.

`getLocalDateISO(new Date())` использует локальные компоненты даты пользователя,
а не `toISOString()` (UTC). Для детерминированных тестов можно явно передать
`today: '2026-10-25'`. Если текущий пробег неизвестен (`null`), проверка
порога по пробегу не выполняется, но проверка даты остаётся доступна.
Результат **не записывается в план** и не вызывает фоновых уведомлений.

Проверка: `node --test tests/fe021-maintenance-due.test.mjs`, `npm test`.
Отображение состояния и отметка выполнения относятся к FE-022.

### FE-022 — раздельные планы и отметка выполнения

`pages/MaintenancePage.js` экспортирует `groupMaintenancePlans(plans, options)`, `createMaintenancePlanList(plans, options)` и `markMaintenancePlanDone(id, options)`. Первый метод группирует массив по сохранённому статусу и вычисляет для активных планов `due` из FE-021; второй отвечает за отображение и доступную кнопку; третий изменяет только указанный план в `autojournal_v1_plans` (FE-006), не затрагивая записи журнала. После отметки список перестраивается без перезагрузки, на странице есть ссылка для отдельной записи фактического ТО. Проверки — `tests/fe022-maintenance-status.test.mjs`.


### FE-023 — Ближайшее ТО на главной

Главная страница показывает одну активную работу из `autojournal_v1_plans`,
её контрольную дату и/или пробег, состояние «Запланировано» или
«Требует внимания» и ссылку `#/maintenance`. Выполненные планы исключены.
Расчёт по пробегу использует **сохранённый** текущий пробег из раздела
«Мой авто» — демонстрационная карточка автомобиля на главной пока не связана
с хранилищем. Если нет активных работ, виден понятный пустой блок.
Повреждённое хранилище не подменяется фиктивными планами.

При выборе ближайшей работы сначала показывается ТО, срок которого уже
наступил. Для будущих работ приоритет у ближайшей контрольной даты;
если дат нет — выбирается минимальный остаток километров. При неизвестном
пробеге планы только по километражу показываются после планов с датой.
Это детерминированное правило: километры нельзя достоверно перевести в дни
без статистики поездок. Список и статус обновляются при возвращении на главную.
Третья сводная карточка теперь показывает реальное число активных работ ТО,
а не демонстрационную единицу.


### FE-024 — безопасные состояния UI

`components/HomeCarCard.js` читает переданный результат `readCar()` и отображает реальный автомобиль или пустое/ошибочное состояние вместо статического примера. `components/SuccessNotice.js` даёт единый доступный `role=status`.

`utils/flashNotice.js` передаёт одно подтверждение от формы новой/редактируемой записи в журнал, не трогая `localStorage`. Сохранение автомобиля и плановых работ, удаление записи и отметка выполненного ТО используют тот же вид сообщения. Сбои сохранения не закрывают формы и не стирают введённые данные. `src/main.js` показывает общее предупреждение чтения, но не уничтожает специальные пустые состояния каждой страницы.

### FE-025 — доступность

`components/FormField.js` поддерживает текст ошибки с `aria-invalid`, `aria-describedby` и `aria-errormessage` без удаления штатных подсказок. Формы автомобиля (`CarPage`), журнала (`NewServiceEntryPage` / `EditServiceEntryPage`) и плана ТО (`MaintenancePage`) сообщают об обязательных полях и подписаны для вспомогательных технологий. Общая таблица стилей содержит контрастные состояния `:focus-visible` для обеих тем фона. Ручной проход Tab/Enter/Shift+Tab: `tests/fe025-manual-check.md`.

### FE-026 — адаптивная компоновка

`tempPage/styles.css` расширен правилами FE-026 для переносов текста в
`HomeCarCard`, истории `JournalPage`, карточке `CarPage`, списке `MaintenancePage`
и сводных карточках. Динамические строки могут не иметь пробелов, поэтому
у соответствующих контейнеров используются `min-width: 0` и
`overflow-wrap: anywhere`. Мобильные кнопки форм сохраняют читаемый текст и
доступный размер. JavaScript-логика и хранилище не меняются.

Структурные регрессионные тесты: `tests/fe026-responsive-layout.test.mjs`;
ручной чек-лист — `tests/fe026-manual-check.md`.


## FE-027 — проверка устойчивости localStorage

`tests/fe027-storage-resilience.test.mjs` проверяет реальное API FE-006
и операции страниц FE-008/010/012/020/022: чистое хранилище, восстановление
после повторного чтения, отказ чтения/записи, повреждённый JSON, независимость
трёх ключей и запрет перезаписи данных при ошибке.

Команды: `npm run test:storage` и `npm test`. Ручной чек-лист:
`tests/fe027-manual-check.md`. Ошибка чтения не является признаком пустого
профиля: страницы показывают предупреждение и не перезаписывают повреждённые
данные. При намеренной очистке localStorage восстановление невозможно без
внешней резервной копии (в MVP она не предусмотрена).


FE-028: основной пользовательский сценарий, негативные проверки и карта US/AC покрыты тестами `tests/fe028-acceptance.test.mjs` и `tests/fe028-e2e-browser.py` (не требуют изменения функционального JS).
